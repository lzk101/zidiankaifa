## DEC-001　两把尺子的口径与分工（本迭代用哪把）

**决定**：
本迭代**以尺子 R 为主尺、尺子 B 为副尺，两把都要达标，另加尺子 A 作参考**。

| 尺 | 定义（文件:行） | 分母口径 | 基线实测 | 本迭代目标 |
| --- | --- | --- | --- | --- |
| **A（主）** | `packages/core/test/related.mjs:144-150` | `words_i18n lang='ru' AND length(word) BETWEEN 4 AND 12 AND rowid % 97 = 0` → **791 词** | **30.8%**（244/791） | **> 45%**（硬门槛，断言须从 `>=0.25` 改为 `>=0.45`） |
| **B（副）** | `packages/data-pipeline/measure_ru_breakdown.mjs`（seed `20260913`, N=800） | **有俄语词源的**俄语词（池 31,193）抽 800 | **38.1%**（305/800） | **≥ 45%** |
| **C（参考）** | 见 `.board/_tmp/probe_ru_measure.mjs` | `words_i18n lang='ru' AND rowid % 97 = 0`（**无词长过滤**）→ 1,043 词 | **32.6%**（340/1043） | **不设门槛**，只要求「不得低于基线 32.6%」并如实报告 |

**理由**：
1. **任务书里「尺子 A 的分母应是全部俄语主词条（101,512）」（派单原文用的是标签 A，其指代对象即本文件的尺子 R）与代码不符**——实测 `related.mjs:144` 是 `rowid % 97 = 0` 的确定性抽样，且有 **词长 4–12** 过滤，分母恰为 791。按 101,512 全量算得到的是**另一把尺子（本文件的 A）**：主管全量精确值 **33,441/101,512 = 32.9%**，本 agent 1/97 抽样核验 32.6%（340/1,043），二者在 95%CI ±2.9pp 内一致。**以代码为准，不以转述为准。**
2. **「30.8%」这个数字的出处已被锁定为尺子 R**：`docs/交接文档.md` §5.2 的「俄语拆解覆盖 30.8%」与 `related.mjs:150` 的断言输出完全一致，故 A2 的「>45%」目标原本就是对尺子 R 说的，A 必须作主尺。
3. **尺子 B 必须同时用，不能只当参考**：它量的是「有词源的词」（≈常见词代理），用户实际查的多是这类词；若只优化 R 而 B 不动，等于在冷僻词上刷分。B 的余量（21.8pp）比 R **更容易**消耗（B 只需 +6.9pp = 55 词，占其余量 **32%**；R 需 +14.2pp = 112 词，占其余量 **68%**），故对 B 提同样的 45% 并不过分。
4. **尺子 A 只作参考、不设门槛**：它是本 agent 为消除「词长过滤是否掩盖问题」的疑问而新增的，此前无人使用；给新尺子设硬门槛会在无基线共识的情况下制造争议。但它的值必须报告，因为它能揭穿「靠缩短分母刷分」。
5. **两把尺子的分母都不得改动**（见 REQ.md §1.6-3）。改分母等于改尺子。

**提出方**：需求管理 agent（依据 `related.mjs:144` 与 `measure_ru_breakdown.mjs` 源码实测）

## DEC-002　优先级排序：正确性 > 覆盖率；尺子 R > 尺子 B

**决定**：冲突时的优先级从高到低：
1. **AC-1 既有 226 项测试全绿**（含 `related.mjs` §A–§D 每条既有期望值逐字不变）
2. **AC-4 20 词判别集反例全绿**（误拆率 = 0%）
3. **AC-5 已能拆解的 889 词不得出现「可拆 → 不可拆」回退**
4. **AC-2 尺子 R > 45%**
5. **AC-3 尺子 B ≥ 45%**
即：**若提升覆盖率必须牺牲正例，则放弃覆盖率，按实际值交付并书面说明，不得为达标而伤正例。**

**理由**：
1. 本项目在 `breakdownWord` 上有**连续 4 次回退**的真实记录（`AGENTS.md` §4.1：`root minLen 2→3`、`hasRootBefore`、`insideRoot`、阈值 0.5→0.55），**每一次都是因为伤了正例**。这条优先级不是保守，是把已验证的教训固化成规则。
2. **危害不对称**：误拆（把 `сегодня` 拆出 `год-`）会直接污染用户可见的「同根词族」与「词根表」，是**离散的正确性缺陷**，用户一旦看到就会失去对数据的信任；覆盖率不足只是**功能稀疏**，是连续可后续改进的指标。
3. 覆盖率是可以在后续迭代继续抬的存量指标，而信任损失不可逆。

**提出方**：需求管理 agent（依据 `AGENTS.md` §4.1 反面教材）

## DEC-003　20 词正反例判别集：由测试 agent 独立建，开发 agent 不得编辑

**决定**：
- **建立者**：**测试 agent 独立建立**，不得与开发 agent 共用草稿。
- **文件**：`packages/core/test/ru_morph.mjs`（可 `node` 直跑，退出码 0/1）。**测试 agent 已于 2026-09-16 按主管 T3 建好（156 行；正例 10 + 反例 10，含 `сегодня`/`стетоскоп`/`арест+Краков` 三条真实误拆回归）**——本 agent 首版拟名 `ru_breakdown_gold.mjs`，**以实际落盘文件为准**（本节 2026-09-16 修订，避免 DoD 引用一个不存在的文件名）。测试 agent 独立发现的**新**缺陷另放同目录 `ru_morph_defects.mjs`，**不计入「20 词全绿」口径**。
- **构成**：**10 正例 + 10 反例**。
  - **正例**＝词内确实存在词素边界，断言「拆解结果包含指定词根」（不逐字写死词尾变体）。
  - **反例**＝单词根词／不可再分，或「规则一放宽就会假命中」的诱饵，断言「必须返回 `[]`」。

- **「全绿」**＝输出 `20 通过 / 0 失败`，退出码 0。
- **改动权**：**只有测试 agent**。开发 agent 本迭代内**禁止编辑该文件**；任何改动需新增 DECISIONS 条目 + 项目主管复核 diff。

**理由**：
1. `AGENTS.md` §4.2 明确「**先写断言，再改代码**」；§4.1 的反面教材直接写「**应在前两版失败时就抽 5 个正例 + 5 个反例建判别集**」——判别集本该在 4 次回退发生前就存在。
2. **独立性是有效性的前提**：若开发 agent 自己写期望值，就是自己出题自己判卷，会（有意或无意地）把期望值调成当前输出，判别集退化为「变更快照」。由测试 agent 独立建，才能构成真正的外部约束。

## DEC-004　人工审定门：用户是词素库新增的唯一最终审定人，否决永久生效

**决定**：`roots_ru.json` **任何新增候选**，必须经**用户本人逐条确认**才可落库。流程：
1. `analyze_ru_morphemes.py` 产出候选 → `_ru_compound_candidates.json`（**原始素材，不是提案**）。
2. 每个候选上报前必须带齐**四要素**：词素+建议释义+kind / **词源依据**（`word_etymology` 里的构词成分或同族词证据）/ **实测边际增益**（加入后新覆盖多少词，在尺子 R/B 上实测）/ 3–5 个例词。
3. 项目主管整理成用户易读表格，**逐条**向用户提问取得「同意 / 否决」。
4. 只有同意的候选写入 `packages/data-pipeline/roots_ru.json`；随后必须重建词素表（`python packages/data-pipeline/build_db.py morphemes`）。
5. **用户否决的候选必须记入本文件**（候选词素 + 否决理由 + 日期 + 提出方＝用户），**后续迭代不得在无新证据时重复上报**。唯一解锁条件＝出现**新的词源数据源**（对应 A1）。

**理由**：
1. `docs/交接文档.md` §6-A2 原文即写「自动挖矿曾试过并被否（**同前缀 ≠ 同源**，TOP40 全是噪声），需**人工审定**」——这是项目已付出的代价，必须固化为流程而不是留在文档一句话里。
2. **「词源依据」是人工审定与失败的自动挖矿之间唯一的分界线**：自动挖矿按「高频同前缀」排序，而 `рас-` 组混进了 `раса`/`Расти` 这类非同源词（见 A3）。要求提供词源证据，等于把「同形」升级为「同源」。
3. **「实测边际增益」避免浪费用户的审定时间**：让用户去判断一个只能多覆盖 2 个词的候选，性价比极低；按增益排序后，用户只需审定 Top-N。
4. 用户是产品的最终意志来源；词素库是**语义断言**（「这个词含这个义素」），语义正确性只能由人来负责，模型无法自证。

**提出方**：需求管理 agent（依据 `docs/交接文档.md` §6-A2 与用户明确要求）

## DEC-005　45% 的定位：**目标而非门槛**（有条件可达）

**决定**：
- **保留 `>45%` 作为本迭代的目标值**（AC-2/AC-3 仍按 >45% 写断言并让 CI 先红）。
- 但把 45% 定性为**目标（goal）而非绝对门槛（gate）**：若在「226 项全绿 + 20 词反例全绿」的前提下用尽手段仍 <45%，**允许按实际交付值收尾**，条件有三：
  1. 必须**书面说明**未达标的原因（含余量构成与已尝试的规则；即 REQ.md §5.2 的证据链格式）；
  2. 断言下限落到实际交付值并**留 2pp 回归余量**（例：交付 41.2% → 断言 `>= 0.39`）；
  3. **降级必须由用户拍板**（不可由项目主管或开发 agent 自行决定）。
- **不得**为达 45% 而放宽 AC-4 反例（DEC-002 优先级更高）。

**理由**（证据链见 REQ.md §5.2）：
1. **45% 不被词素库封顶**：当前 441 条词素下，放弃全部位置规则后的**严格上界**为尺子 R 51.7% / 尺子 B 59.9%（已做合法性自检，违例 0 条）。所以 45% 在数学上够得着——**这是「可达」的一面**。
2. **但余量全部落在「为防误拆而设」的规则上**：165 个可争取词中，**94 词含「库内多字符前缀但不在词首」**，放宽它才能救——而 `index.ts:766` 的「前缀只能起于词首」正是为阻挡 `principle → in-`@1 而设；另有 **61 词**是词首单字符前缀（`в-`/`с-`/`у-`/`о-`）缺紧邻词根支撑，而 `index.ts:773-775` 注释点名放宽它会导致 `вода → в-|ода`、`страшный → с-|трашный`。**即：可达路径与「不伤正例」直接对撞**——这是「有条件」的一面。
3. **加库路线在本迭代不可行**：要把尺子 R 从 30.8% 抬到 45%，需多覆盖样本 113 词 ≈ 全量约 **1.1 万词**；即便每个新词根带动数十个同族词，也需**数百至数千条**新词素，且每条都要用户审定（DEC-004）。**一个迭代内不可能。**
4. **调阈值是另一条杠杆但同样要过反例关**：阈值降到 0.45 → 上界 63.7%/70.4%，单靠它就够跨 45%；但 `index.ts:708-709` 的阈值本意就是拦 `difficult→cul`、`business→-ness` 类碎片误拆。故这条路**必须由 20 词反例集把关**，不能单方面降阈值。
5. **现实交付区间预计 35–42%**。把 45% 定性为目标而非门槛，可避免开发 agent 在末期为凑数字而牺牲正确性——那正是 `AGENTS.md` §4.1 记录过的行为模式。

**提出方**：需求管理 agent（用户要求「若你认为 45% 可能不可达，现在就写出来」）

## DEC-006　A6 天花板的量化与其对 45% 的影响

**决定**：把 A6（`луна`/`небо`/`река`/`гора` 等单词根词无法拆解）量化为以下事实，并在本迭代交付说明中引用：
- 尺子 R 791 词中，**「严格上界 < 0.55」（加库才能救）= 382 词 = 48.3%**。这就是 A6 现象在覆盖率上的份额。
- 其中**「词内不存在任何已知词素」的只有 104 词 = 13.1%**（例：`Богъ`/`Мальта`/`Эдем`/`азид`/`барабан`）。
- 其余约 35pp 是「**有词素，但覆盖不到 55%**」——即**瓶颈是「覆盖深度」而不是「词素缺失」**。
- A6 点名词实测：`луна` / `небо` / `река` / `гора` 均无拆解（`луна`/`небо`/`река` 词内可及某词素但覆盖不足，`гора` 完全不可及）。
- **结论：45% 的天花板不由 A6 决定。** 靠「给单词根词补一个词根条目」（如 `стол-` 那样）、从而以「单词根 = 100% 覆盖」的方式救 A6，虽是合法路径，但需要数百条人工审定词素，本迭代不可行（DEC-005 理由 3）。

**理由**：
1. 用户要求「量化这个天花板的影响，这直接决定 45% 是否可达」——量化结果表明**它不是决定性因素**：真正卡住 45% 的是规则冲突（DEC-005 理由 2），A6 只占 48.3% 中的一部分，且大部分是可加库解决的**存量**问题。
2. 把「13.1% 完全无词素」与「35pp 有词素但覆盖不足」拆开，对开发 agent 有直接指导意义：**不要以为「加词素就能解决一切」**——对那 35pp，加词素与改规则是两条不同的路，收益差别很大。
3. `стол → ['стол-']`（`related.mjs:129`）证明「单词根词入库后以单片段 100% 覆盖通过」是现行算法**已支持且已在使用**的机制，故 A6 不是原理性障碍，只是工作量问题。

**提出方**：需求管理 agent（用户要求量化 A6 冲突）
