## 1. REQ-A2-001 俄语拆解覆盖率

### 1.1 背景与现状（全部实测，非文档转述）

项目里有**三把不同的尺子**在量「俄语拆解覆盖率」，此前文档把它们的数字混为一谈（都写成 30.8%），这是本迭代最先要钉死的歧义。

> **⚠ 尺子标签已与项目主管的 `.board/BASELINE.md` §4 统一（DEC-012）**：**R（主尺，★权威★）/ A（参考尺）/ B（副尺）**。
> 本 agent 首版文档曾用 A/B/C，与主管标签**撞车**（本 agent 的 A ＝ 主管的 R；本 agent 的 C ＝ 主管的 A），语义交叉会导致 T2/T5 的 agent **按错尺子判 45%**（两把尺子基线 30.8% vs 32.9%、上界 51.7% vs 54.1%，难度不同）。已全部改为主管标签，并把「全词条」尺子改用主管的**全量精确值 32.9%（33,441/101,512）**；本 agent 的 1/97 抽样值 32.6%（340/1,043）降级为交叉验证（二者在抽样 95%CI ±2.9pp 内一致）。

| 尺 | 位置 | 分母口径 | 样本量 | 实测基线 | 严格上界¹ | 可争取余量 |
| --- | --- | --- | --- | --- | --- | --- |
| **R（主尺，★权威★；与 `.board/BASELINE.md` §4 同名）** | `packages/core/test/related.mjs:144` | `words_i18n` 中 `lang='ru'` **且词长 4–12** 且 `rowid % 97 = 0` | 791 | **244/791 = 30.8%** | **409/791 = 51.7%** | 165 词 = 20.9pp |

¹ **严格上界**＝在**不新增任何词素、不降低 55% 阈值**的前提下，放弃「前缀限词首 / 后缀需 ≥3 字符词干 / 单字符前缀需紧邻支撑 / 词首间隙」等全部位置规则后，用不重叠最大覆盖 DP 得出的比例。它是「当前 441 条词素库下**无论如何调算法都不可能超过**」的数学上界。已做合法性自检：对全部 3 个样本逐词验证「上界 ≥ 实测覆盖度」，**违例 0 条**（脚本 `.board/_tmp/probe_ru_ceiling2.mjs`）。

**基线事实**（实测，修正三处文档表述）：

1. 尺子 R 的**分母不是 101,512**。它是 `rowid % 97 = 0` 的确定性抽样（791 词，等于 77,689 个 4–12 字符俄语词的 1/97）。任务书里「分母应是全部俄语主词条（101,512）」的说法与代码不符——若真按 101,512 全量算，还会把 1,036 个 2–3 字符词与 22,787 个 13+ 字符词算进来，得到的是尺子 A 的 32.6%。
2. **尺子 R 与 B 的 30.8% 是巧合，不是同一件事。** 词源覆盖 31,256/101,512 = 30.8%；尺子 R 拆解 244/791 = 30.8%。两个不同的分数同值，文档 §5.2 把「俄语拆解覆盖」写成 30.8% 时引用的是尺子 R，但读者极易误以为它等于尺子 B（实为 38.1%）。
3. `word_etymology(ru)` 有 31,256 行，其中 **63 行**的 word 不在 `words_i18n(ru)` 中，故尺子 B 的池是 **31,193**（不是 31,256）。
4. 词长分布：2–3 字符 1,036 / 4–12 字符 77,689 / 13+ 字符 22,787。13+ 长词拆解率更高（多为复合词），故尺子 R 的词长过滤使其**偏保守**（R 30.8% < A 32.9%，A 为全量精确值）。
5. 俄语词素库 441 条 = 前缀 185 + 词根 163 + 后缀 93（`morphemes WHERE lang='ru'`）。
6. **「分母有水分」的假设已被实测否定（DEC-013）**：主管 `BASELINE.md` §5.2 提出 `words_i18n` 含**纯词缀条目**（`-ед`/`-ец`/`-ировать`/`-ость`/`-ский`…）与**专名**（`Абакан`/`Австралия`/`Иисусъ`），它们拉低分母且原理上不可拆，疑为 45% 的天花板。实测（`.board/_tmp/probe_ru_denominator.mjs`）：尺子 R 的 791 词中**纯词缀条目仅 4 词（0.5%）+ 首字母大写专名 10 词（1.3%）**，合计 14 词；**全部剔出分母后覆盖率为 30.7%（不升反降 0.1pp，因 4 条词缀条目里有 2 条本就能拆）**，只剔专名为 31.0%（+0.2pp）。全量口径：纯词缀条目 326（0.3%）+ 首字母大写 1,280（1.3%）+ 旧正字法形（含 `ъ`/`ѣ`/`і`）611（0.6%），合计 ≤2.2%。→ **改分母对 45% 的贡献 ≤0.3pp，救不了 45%**；故本迭代**不提「把非词词条剔出分母」这条需求**，也不占用用户决策额度（§1.6-3 的「不改分母」非目标因此继续成立，且现在有了实测支撑）。真正的天花板在规则层，见 §5.2。

### 1.5 人工审定门（词素库新增的唯一合法入口）

> 依据：`docs/交接文档.md` §6-A2 明确「自动挖矿曾试过并被否（同前缀 ≠ 同源，TOP40 全是噪声），需**人工审定**」。本迭代把这句话固化为流程。

**流程（不可跳步）**：

1. **产出候选**：`python packages/data-pipeline/analyze_ru_morphemes.py` → `packages/data-pipeline/_ru_compound_candidates.json`。
   注意：该脚本的输出是**原始素材，不是提案**——它的历史失败原因就是把「高频同前缀」当成了「同源」。
2. **排序与量化**（项目主管/数据 agent）：每个候选必须带齐四要素才可上报——
   - `词素` + 建议中文释义 + 建议 kind（前缀/词根/后缀）
   - **词源依据**：`word_etymology` 中能支撑该词素的构词成分或同族词证据（**这是与失败的自动挖矿唯一的区别**）
   - **实测边际增益**：加入后能新覆盖多少个词（必须在尺子 R/B 上实测，不是估算）
   - 3–5 个例词
3. **用户审定（最终审定人 = 用户本人）**：由项目主管整理成用户易读的形式（表格，一行一个候选，含上述四要素）向用户提问，**逐条**取得「同意 / 否决」。
4. **落库**：只有用户明确同意的候选才写入 `packages/data-pipeline/roots_ru.json`；随后必须重建词素表（D7）。
5. **否决永久生效**：用户否决的候选必须记入 `.board/DECISIONS.md`（含候选词素、否决理由、日期、提出方＝用户），**后续迭代不得在无新证据的情况下重复上报**。新证据 = 新的词源数据源（对应 A1）。

**本迭代的门槛定位（重要，见 DEC-007）**：因 AC-2 在**当前 441 条词素库**下已有 51.7% 的数学上界，**A2 的关键路径不经过人工审定门**。该门是「可选辅助路径」，其耗时（用户逐条确认）不应成为本迭代的排期风险。若开发 agent 判断必须加库才能达标，须先向项目主管报备，因为那会把用户拉进关键路径。

### 5.2 45% 可达性的证据链（结论见 DEC-005）

1. 当前命中 244/791（30.8%），**严格上界 409/791（51.7%）**——45% **不被词素库封顶**。
2. 但有 165 词（20.9pp）属「上界够、当前失败」，即**全部余量都在规则层**。其构成：
   - **61 词**：词首是单字符前缀（`в-`/`о-`/`с-`/`у-`），但**紧邻处没有 ≥3 字符的词根**，被 `packages/core/src/db/index.ts:776` 的「单字符前缀需紧邻支撑」规则拒绝。这些词的上界恰恰是靠「前缀 + 远处后缀」凑够 55% 的（例：`вдыхать` = `в`@0 + `-ать`@4 = 4/7 = 0.57）。**放宽这条规则正是历史上导致 `вода → в-|ода`、`страшный → с-|трашный` 误拆的原因**（`index.ts:773-775` 注释）。
   - **38 词**：词首是多字符前缀（`авиа-`/`без-`/`дез-`/`би-`），其余部分需靠**非词首的前缀**才能凑够覆盖。
   - **其它 66 词**：无词首前缀线索（多为专名与派生词）。
   - **合计 94/165 词含「库内多字符前缀但不在词首」**——放宽前缀位置规则才能救，而该规则是 `index.ts:766` 为阻挡 `principle → in-`@1 而**刻意设置**的。
3. 阈值敏感性（严格上界视角，说明另一条杠杆）：阈值降到 **0.45** → 尺子 R 上界 63.7% / 尺子 B 70.4%；降到 **0.50** → 61.9% / 69.5%；降到 **0.35** → 75.5% / 80.0%。即**单靠调阈值就足以跨过 45%**，但阈值的存在意义正是拦住「碎片式误拆」（`index.ts:708-709` 注释点名 `difficult→cul`、`business→-ness`）。**这条路必须由 20 词反例集把关。**
4. **加库路线不可行**：尺子 R 样本是 77,689 个 4–12 字符词的 1/97。要把 30.8% 抬到 45% 需在样本里多覆盖 113 词 ≈ 全量 **约 1.1 万词**；按每个新词根带动数十个同族词估算，也需**数百至数千条**新词素，且每条都要用户逐条审定（§1.5）。→ 不可能在一个迭代内完成。
5. **余量消耗比的硬数字（判定 45% 难度的关键）**：尺子 R 要到 45% 需命中 **356/791**，即从 244 再抢 **112 词**；而全部可争取余量只有 165 词 → **必须吃掉 68% 的余量**（副尺 B 只需 55/174 = **32%**）。而这 165 词中有 **94 词（57%）** 的救法都指向 `index.ts:766`「前缀必须在词首」这条**刻意为阻挡 `principle → in-`@1 而设**的规则（见上条）。**这就是 45% 的真实难度：不是数学上够不着，而是必须动最不该动的那条规则。**

### 6.3 两个歧义的裁定（主管 Q1 / Q2）

**Q1 裁定：D2（V9-5，词中空洞无上限）不在本迭代范围内 ⇒ AC-2 改为「30 红 → 0 红」**，D2 3 条红**允许留红并顺延 v0.10.0**。理由五条：
1. **机制层不同**：D2 是 **DP 空洞长度约束**（`землетрясение` 跳 `ряс`、`водопад`），V9-1/V9-2 是**词素语义核证**；两者修法、判据、反例集都不同。
2. **无判别实验支撑**：T19 的判别实验只覆盖 V9-1/V9-2；把 D2 纳入即**违反「先判别实验再改代码」**（`AGENTS.md` §4.2、用户既定红线）。
3. **与用户红线最易冲突**：D2 的修法天然是**新增一条空洞长度上限规则/阈值**，而用户拍板「**不动任何阈值**」。
4. **可归因性**：若纳入，AC-2 失败将**无法区分**「防假拆解没做到」还是「空洞上限没做」——验收失去诊断力。
5. **范围纪律**：DEC-002「正确性 > 覆盖率」+ 主管既定原则「宁可范围小而全部达成」。

**Q2 裁定：H-d 可以用，但必须走「条件式 AC + 独立留红断言 + 冻结名单」三件套**（展开见 §6.4）。**可复用的先例**＝v0.8.0 的 `ru_morph_goals.mjs`：把达不到的目标**拆成独立文件**（留红断言 exit 2），让**主链恒绿**、目标**不被删除也不被改软**。

### 6.4 H-d（不可行声明）与「诚实交付」条款（AC-10 展开）

1. **不删、不改软**：判为 H-d 的条目**保留在库**（不删词素、不动阈值），并保留**独立的、可运行的留红断言**；断言标签加 **`H-D` 前缀**以便机械统计（沿用 `ru_morph_goals.mjs` 的「独立文件 + 主链不阻塞」模式）。
