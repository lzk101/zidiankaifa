# 📋 产品需求总结：「我的电子辞典」

> 文档角色：产品经理需求总结（本会话）
> 需求来源：主会话「开发自己的电子辞典」 + 数据文件创作子任务 + 前端 UI 实现子任务 + `README.md`
> 数据截至：2026-09-13（**v0.4.0 发布后**——含 v0.2.1 数据管线、v0.3 俄语词源、v0.4 自动更新）

---

## 1. 产品概述

**一句话定位**：一款自研的个人电子辞典——以「语言发展流程」为主线（词源分类 → 词形演变 → 词根词缀拆解）组织单词学习，支持查词、发音、生词本、剪贴板取词与跨端云同步，最终交付 Windows 桌面 `.exe` 应用。

**技术定位**：React 18 + TypeScript + SQLite（`node:sqlite`，无原生编译依赖）+ Electron 37 桌面壳 + Node 内置 HTTP 同步服务；同一套前端以 PWA 覆盖手机端。

**发布目标**：公开 GitHub 仓库 `https://github.com/lzk101/zidiankaifa`。

## 2. 背景与目标

| 项 | 内容 |
|---|---|
| 原始诉求 | 「我想要开发一款自己的电子辞典」（主会话首条消息） |
| 目标用户 | 开发者本人（个人学习工具） |
| 核心价值 | 用词源/词根/词形的**语言发展视角**理解单词，而非死记硬背 |

## 3. 功能需求

### F1 查词（核心）
- 大字词条 + 音标（无音标显示「暂无音标」）+ 发音按钮 + 收藏按钮
- 柯林斯/牛津星级（0 星隐藏）；考试标签（中考/高考/四六级/考研/托福/GRE/雅思）
- 词频展示（「语料频次 第 N 位」）；词性 + 英英释义 + 英汉释义（换行处理）
- 未收录态：显示「未收录该词」+ 相近词建议（点击可查）
- 启动时自动查最近一次查过的词（localStorage 记忆）

### F2 发音
- 系统 TTS（`speechSynthesis`，en-US 优先，其次 en-GB/en 前缀语音），返回 Promise
- 桌面/浏览器统一走 Web Speech API

### F3 词源分类（用户重点反馈项）
- 三层数据：词级演变链（Etymological Wordnet，135k 词）+ **Wiktionary（wiktextract）词源详解**（词源原文中文/英文 + 结构化派生链）+ 语源语言判定
- 展示：语言来源（如「拉丁语」）+ 演变链（箭头 chip 串联）+「演变 N 级」；**同源词（cognate）单独标注**（灰底虚线 +「同源」标签），避免把「与英语 water 同源」误读为「源自英语」
- ⚠️ 用户反馈「**词源发展不够详细**」→ 已升级为 wiktextract 详解展示（15.5 万词条）
- **构词路径一体化**（v0.2 起）：词源卡内置「构词成分」行（词素 + 含义 + 来源），把**词素级拆解**与**词级演变链**串成一条发展路径
- **俄语词源**（v0.3 起，v0.4.1 补漏、v0.5.0 修标注）：**31,256 条**（中文 14,224 + 英文 30,322），含 27,852 条结构化派生链；v0.5.0 修正来源标注——原先 20,060 条（64%）把**资料出处**（`source='en'`）当成**语源语言**显示「源自 英语」，现按规则细分为「构词 7,706 / 真实语源（原始斯拉夫语 2,691、拉丁语 751、法语 650…）/ 确有借自英语 195 / 无依据置空 11,910」

### F4 词形演变
- 按 form_type 分组：原型/复数/过去式/过去分词/现在分词/第三人称单数/比较级/最高级/其他变体
- 词形 chip **点击即查**该词形

### F5 词根词缀拆解
- 内置词素库 **888 条**（英语 456 + **俄语 432**：前缀 185 / 后缀 93 / 词根 154）：root ≥150 / prefix ≥60 / suffix ≥50（六字段结构：`morpheme/kind/meaningZh/meaningEn/origin/examples`）；俄语部分由 Wiktionary 构词模板与词表复合切分**数据驱动**扩充（v0.4.3：145 → 432）
- **贪心最长匹配**（v0.2 重写）：词根/前缀/后缀**一体比较取最长**（`bio` 优先于 `bi`，修复误拆）、支持**一词多词素全命中**、词头保留 1 字符间隙噪声规则、词中间隙放行；例词点击即查
- **俄语拆解**（v0.3 起，v0.4.3 修复）：①单字符前缀**紧跟**验证（в-/с-/у-/о- 后必须紧邻 ≥3 字符词根/后缀，避免 `вода → в-|ода`、`страшный → с-`）；②后缀屈折核心匹配（`-ость` 核心 `ост` 吸收 `-и/-остью`，核心须 ≥3 字符）；③**ё/е 等价**匹配（`весёлый` 命中 `весел-`）
- 整词字母串渲染，命中词素着色：**root 蓝 / prefix 紫 / suffix 绿**，未命中字母灰色
- 词素色块展示中文含义 + 来源语言 + **例词 chips**；无数据显示「暂未拆解」

### F6 生词本
- 四态管理：新学 / 学习中 / 已掌握 / 已暂停（徽章循环切换）
- 状态过滤（全部/四态）、删除、回车添加、数量统计

### F7 剪贴板取词（桌面端）
- 复制单词自动弹出释义浮窗（右下角卡片，8 秒自动关闭，发音 + 收藏 + 关闭）

### F8 设置
- 同步服务器地址（本地存储）；同步按钮（显示推送/拉取数量）
- 主题切换（浅色/深色，写入 localStorage + `html[data-theme]`）
- **软件更新**（v0.4）：状态显示、检查更新、下载进度（百分比/速率/已下载量）、立即重启安装、打开发布页、启动时自动检查开关（`zidian-auto-update` 持久化）；浏览器模式提示手动刷新，便携版引导手动下载
- 关于信息（版本 **0.5.0**、词库来源 ECDICT 等）

### F9 云同步
- 自建轻量 Node 服务：查词代理 + 生词本 **last-write-wins 合并（含删除墓碑）**，可选 Bearer Token 鉴权
- REST 端点：`/health`、`/api/v1/lookup`、`/api/v1/suggest`、`/api/v1/breakdown`、`/api/v1/book`、`/api/v1/book-groups`（生词本 × 词素分组，v0.2 起）、`/api/v1/sync`
- 双后端解析层：Electron 模式走 IPC（`window.dictAPI`），浏览器模式走 REST + localStorage

### F10 多语言支持（新增需求：俄语）
- 内置**俄语**：**10.15 万主词条**（v0.4.4 已清出 5.7 万条被误建为词条的屈折形；中文释义 + IPA 音标 64.2% + **变格变位 62.8%（109 万词形）+ 反查表 63.35 万行** + 真人音频链接 10.4% + **词源 31,256 条 = 30.8%**，数据来自中/英维基词典）
- **变格变位结构化表格**（v0.2）：名词=格×数、动词=人称×时态、过去时=时态×性数、形容词=性数格，标签用 `RUS_TAG_LABEL` 中文
- **语言切换器**（自动/英语/俄语，`zidian-lang` 持久化）+ 中文反查**英俄交错**展示 + 联想项 🇬🇧/🇷🇺 徽章；生词本按语言标注
- 结构预留多语言扩展（ja/ko/fr… 可直接接入，`lang` 列已贯通数据层到 UI）

### F11 桌面应用打包（新增需求）
- Electron 壳（contextIsolation + preload 桥）+ electron-builder
- **最终交付物：Windows `.exe` 安装/可执行文件**（安装版 + 便携版）

### F12 发布 GitHub（新增需求）
- 公开仓库发布：`https://github.com/lzk101/zidiankaifa`

### F13 自动更新（新增需求，v0.4）
- **应用内闭环**：检查 → 下载 → 重启即装（electron-updater + GitHub Releases）
- 启动静默检查（可关闭）；顶部条幅提示；**blockmap 差分下载**（180MB 包仅传变化分块）；sha512 校验
- 便携版无自更新能力 → UI 引导手动下载；`ZIDIANKAIFA_UPDATE_URL` 可覆盖更新源（镜像/内网）

|---|---|

## 9. v0.2 需求：用户实测反馈 4 项问题（2026-08-31）

> 来源：用户实际使用后反馈。以下每项含**实证根因**（本会话对 `dict.db` 与源码核实）与**需求定义**。

### 问题 1（P0）：英语 / 俄语不分开，使用混乱

**根因（代码实证，`packages/core/src/db/index.ts`）**：
- 查词按「输入字符」自动路由：西里尔字符 → 只查俄语；拉丁字符 → 只查英语；**中文输入 → 在英/俄释义里混合搜索，只返回第一条命中**（可能是英语也可能是俄语，结果不确定）
- 联想（suggest）：中文前缀返回 `[...en, ...ru]` 混合列表，**无语言标注**
- UI（`App.tsx` / `DetailCard.tsx`）：无语言切换器；英语词条无语言标识（仅俄语有「俄语」徽章）；同一输入无法主动选择语言

**需求定义**：
- 提供**语言切换器**（英语 / 俄语 / 自动检测，默认自动）
- 中文查询返回**英、俄双结果分区展示**（或语言可切换），不再随机只给一条
- 联想下拉列表每项**标注语言**（🇬🇧 / 🇷🇺）
- 生词本 `book` 表增加 **`lang` 字段**（当前仅 `word` 唯一键，多语言长期冲突风险；同步契约同步升级）

### 问题 2（P0）：词根/词源/词缀与单词发展路径脱节，且词根不明确

**根因（代码 + 数据实证）**：
- 拆解 `breakdownWord()` 是**启发式子串匹配**：前缀/后缀/词根**每类只取一个最长命中**——实测 `telephone` 只出 `phon`（漏 `tele-`）；`unbelievable` 只出 `un-`/`-able`（漏词根 believe）；`biology` 被**误拆**为 `bi(二) + bio(生命)`（前缀误命中，实际是 `bio-` 一个词素）
- 词源（`word_origins.lineage` 演变链 + `word_etymology.chain` wiktextract 派生链，**含 `parts` 构词成分字段**）与词根拆解是**两套独立数据**，界面完全没打通：OriginCard 显示演变链、BreakdownCard 显示词素，中间「词 = 这些词素构成、词素各自从哪种语言来」的**构词路径不体现**
- 中文词源详解 `word_etymology.text_zh` 实测**全部为空**（仅英文 chain 有数据，154,877 词）——中文词源升级目标未真正落地

**需求定义**：
- **构词路径一体化**：以 `etymology.chain.parts`（wiktextract 已含构词成分）为主驱动拆解，替代纯子串启发式；UI 把「演变链 → 构词成分 → 词素含义/来源」串成一条**发展路径**展示（词源卡与词根卡合并或联动）
- **拆解准确率**：支持一词多词素全命中（不只一个 root）；修复误拆（`bio-` 优先于 `bi-` 等长词素优先策略）；验收样例 `telephone / biology / unbelievable / transportation / spectator` 拆解全部正确
- **中文词源补齐**：构建 `text_zh`（wiktextract 中文转储或翻译层），OriginCard 显示中文词源原文
- 词素卡展示该词素的**例词**，例词点击即查（`morphemes.examples` 数据已有，UI 未用）

### 问题 3（P1）：需要知识图谱——通过词根与词缀把生词本联系起来

**现状**：无任何图谱功能；生词本与词素数据互相孤立（`book` 表与 `morphemes` 表无关联查询）。

**需求定义**（MVP 两级）：
- **数据层**：新增图谱查询能力——生词本单词 × 词根/词缀：`word --包含--> morpheme`（复用准确拆解）、`word --衍生自--> 祖先词`（复用 lineage）、`morpheme <-> morpheme` 同类/同源关联
- **生词本「词根分组」视图**（手机/桌面通用）：按命中词根分组展示生词，点词根显示该词根下全部生词 + 词素含义 + 例词——**最小可用版本**
- **图谱可视化**（桌面）：可缩放/平移的词根-单词网络图，节点=生词/词素，边=包含/衍生关系，点节点回跳查词
- 前置依赖：问题 2 的拆解准确率（图谱质量依赖它）

### 问题 4（P1）：俄语内容未完成，变位变格不明确

**根因（数据实证，`dict.db`）**：
- 覆盖缺口：159,127 俄语词条中 **仅 77,727 条有变格变位 forms（48.8%）**；反查表 `i18n_forms` 仅 37,097 行；音标 50%（80,200）；音频仅 6%（9,622）
- 展示缺陷（`DetailCard.tsx` i18n 分支）：变格变位是**扁平 chip 列表**（`f.display + tags.join('/')`），名词的格×数、动词的人称×时态**不成表格**，无法阅读；未按词性区分变格/变位/变形容词

**需求定义**：
- **展示升级**（P1）：变格变位**结构化表格**——名词按「格 × 单复数」表；动词按「人称 × 时态」表；形容词按「性/数/格」表；标签用现有 `RUS_TAG_LABEL` 中文（主格/属格/单数/完成体…）；命中词形反查明确标注来源形式与语法信息
- **数据补全**（P1，管线任务）：补齐剩余 ~51% 词条的变格变位（wiktextract 俄语转储增量构建）；音标、音频覆盖率提升（音频 6% → 目标 ≥30%）
- 俄语词条也纳入「词根/词素」视角（俄语前缀/后缀库，与知识图谱同构）

## 12. v0.3 俄语词源 · 词根词缀（2026-09-13，用户需求「添加俄语词源词根词缀」）

> 目标：把「词源 + 词根词缀」能力从英语扩展到俄语——俄语词条此前 `etymology=null`、`breakdown=[]`（`i18nToDetail` 硬编码空值），用户看不到任何词源与构词信息。

### 12.1 数据源勘察（先勘察后动手）

| 数据源 | 结论 |
|---|---|
| **zh 转储俄语词条** | 163,586 条俄词条，**15,213 条带 `etymology_texts`（中文词源）**，质量极高：вода「继承自古东斯拉夫语 → 原始斯拉夫语 *voda → 原始波罗的-斯拉夫语 *wandō → 原始印欧语 *wódr̥…与英语 water 同源」 |
| en 转储俄语词条 | 442,348 条俄词条，45,686（10%）带英文词源；**28,862 条带构词模板**（`af` 28,901 次、`pre`/`suf`/`bor+`/`cog`…）——可作词素库校验 |
| 俄语词素库 | **不存在**（`morphemes` 表 437 条全是英语词素），须新建 |

**决策**：以 **zh 中文词源为主源**（中文用户可读性最高）→ 新建俄语词素库 → core 支持 lang 化词源/拆解。英语词源文本对中文用户价值低，仅作补充。

### 12.2 交付物

1. **数据层**
   - `packages/data-pipeline/roots_ru.json`：**俄语词素库 145 条**（前缀 50 / 后缀 42 / 词根 53），六字段与英语 `roots.json` 同构；例词经词表校验，**命中率 99.4%（488/491）**——如 `без-`（无、缺乏）、`-ость`（抽象名词）、`вод-`（水）、`теле-`（远）、`фон-`（声音）
   - `packages/data-pipeline/build_ru_etym.py`：zh 转储中文词源 → 简体（OpenCC t2s）→ `word_etymology(lang='ru')`；从中文文本解析**结构化派生链**（语言名 + 词形）→ `chain`；en 转储补英文词源与模板链；`roots_ru.json` → `morphemes(lang='ru')`
   - schema 双端同步加列：`packages/core/schema.ts`（运行时 SCHEMA_SQL）与 `packages/core/schema.sql`（数据管线建表）——`word_etymology.lang`、`morphemes.lang`（默认 `'en'`，老库由 `migrateAddColumn()` 自动 ALTER）
2. **core 查询层**（`packages/core/src/db/index.ts`）
   - `getEtymology(db, word, lang='en')`、`loadMorphemes(db, lang='en')`（按语言缓存）、`breakdownWord(db, word, lang='en')`

## 14. v0.4.1 三项遗留修复（2026-09-13，用户指令「继续1，2，3项任务」）

承接 §12 遗留，本轮处理三项：①俄语词源覆盖率 ②俄语模式 suggest 未接 lang ③拆解 `believ` 词素缺失。

### 14.1 任务 1：俄语词源覆盖率（19.3% → 19.6%）

**勘察结论（先勘察后动手）**：两个转储都已挖到头——
- en 转储（`data/raw/wiktextract-all.jsonl.gz` 2.63GB）中与库重叠的俄语词 107,594 条，其中**库中尚无词源且有任何信号的仅 508 条**，完全无信号 73,962 条（英文维基词典里俄语词多数无词源）
- zh 转储（`data/raw/wiktextract-zh.jsonl.gz` 0.21GB）库中重叠 163,583 条，缺口仅 360 条

**漏失根因 = 大小写 bug**：`build_ru_etym.py` 中 `ru_words = {r[0] for ...}`（库中形如大写的 `Китай`）与 `w = strip_stress(...).lower()`（`китай`）比较，**所有大写开头专名被静默跳过**（Китай/Европа/Москва/Япония/Россия 均有 `pos=name` + `etymology_texts=1` 却未入库）。

**修复与结果**：
- `packages/data-pipeline/build_ru_etym.py`：建 `ru_index = {strip_stress(w).lower(): 原词形}`，`collect_zh(t2s, lang_re, ru_index)` / `collect_en(ru_index)` 改为回填原词形
- `--zh-only` 新增 372 条、`--en-only` 新增 117 条 → 俄语词源 **30,767 → 31,256**（19.3% → **19.6%**），中文 14,224；新增中 **482/489 为大写开头专名**

**但 `lookupWord` 仍查不到这些词源 → 连带挖出两个更严重的查词缺陷**（见 14.4）：库里已有词源，却因大小写规范化与「反查优先」劫持而取到错误的词。

### 14.2 任务 2：suggest 语言隔离

`packages/core/src/db/index.ts` 的 `suggest(db, rawQuery, limit = 20, lang?)` 新增模式分流：`mode = lang === 'en' || lang === 'ru' ? lang : 'auto'`，抽出 `ruPrefix()`/`enPrefix()`/`byTranslation('en'|'ru')`；`lang` 全链路透传（`types.ts` → `sync-server` `/api/v1/suggest?lang=` → `main.mjs` `dict:suggest` → `preload.mjs` → `api.ts` → `SearchBar.tsx` prop）。

**效果**：俄语模式搜中文只回俄语项、英语模式只回英语项、auto 保持英俄交错；西里尔 + `lang=en`、拉丁 + `lang=ru` 均返回空（不再串台）。

### 14.3 任务 3：拆解准确率

- `packages/data-pipeline/roots.json` 437 → **456 条**：新增 16 条真词根（believ/know/tempt/camp/techn/nucle/chiev/cour/self/craft/troubl/holi/belief/every/body/air）+ 本轮 3 条（`-ator` 能产后缀、`-ledge`、`creat`）；`morphemes` 表 **598 → 601 条**（英语 456 + 俄语 145）
- `breakdownWord` 位置约束（`packages/core/src/db/index.ts`）：`prefix` 仅允许词首、`suffix` 与前一词素间隙 ≤1、任意词素间隙 >3 直接跳过 —— **准确率优先**，拒掉 `difficult→-ic`、`principle→in-`、`business→-ine` 这类误拆
- 失败尝试（已回退）：root 最短长度 2→3 会使未拆开数 361→941 且 `учитель` 被误拆为 `у-+чит-`；后缀「必须到词尾」会丢 `писатель/учитель` 的 `-тель`（俄语词干后有连接元音 а）→ 改为「间隙 ≤1」

### 14.4 本轮挖出的两个查词正确性缺陷（比原任务更严重，已修）

**缺陷 A：大小写规范化导致专名走错词条。**
`lookupWord` 先 `normalizeWord`（小写化）再查库，而俄语专名在 `word_etymology` 中按**原词形**存储（`Китай`），SQLite 的 `COLLATE NOCASE` 又**只折叠 ASCII、对西里尔字母无效** → 查 `Китай/Москва/Европа/Япония/Россия` 取不到词源（`Англия` 能取到纯属库里恰好另有小写行）。
修复：新增 `caseVariants(word)`（原词形 → 全小写 → 首字母大写）与 `getByVariants()`，`getOrigin`/`getEtymology`/`getI18n`/`i18n_forms` 反查全部改为**大小写宽容查找**；`lookupWord` 的西里尔分支改传原始词形（不再预小写）。

**缺陷 B：词形反查劫持独立词条（释义张冠李戴）。**
`words_i18n` 中同一词常有**大小写两行**，小写行是 zh 转储给屈折形建的词条，其「释义」只是「X 的属格单数」这类说明：

| 词条 | 释义 | 后果 |
|---|---|---|
| `Франция` [name] | 法国（位于西欧的国家） | 正确义项 |
| `франция` [noun] | фра́нций (fráncij) 的属格单数 | 小写化后命中它 → 查「法国」显示「钫的属格单数」 |
| `Индия` / `индия` | 印度（位于南亚的国家） / и́ндий (índij) 的属格单数 | 查「印度」显示「铟的属格单数」 |
| `дома` | 在家；дом (dom) 的属格单数… | 反查劫持到 `дом`（桌子）→「在家」丢失 |

修复：新增 `isInflectionOnlyGloss()` 判据（按 `；` 分段，**全部**段落匹配「的…格/数/时/式」才算纯屈折说明），两层应用——
1. `getI18n` 命中多个大小写变体时**优先取有实质释义的行**（`Франция` 优于 `франция`）
2. `lookupI18n` 反查时若输入自身有实质释义（`дома`「在家」、`яма`「坑，洞」）则**不劫持**，仍返回自身；纯屈折形（`столом`「стол 的工具格单数」、`банана`、`сентября`）**照旧反查**到主词条 + 格标注

> 该判据经数据核验：`столом/стола/столы/столе/банана/сентября` 全部命中「纯屈折」，`дома/яма/Франция` 全部命中「有实质释义」，无一误判。

### 14.7 v0.4.2 更新行为核验与加固（同日）

**背景**：v0.4.0 安装版实测时曾观察到「检查到新版本后自动进入 `downloading`（DIAG `percent=9`）」，与设计（`autoDownload=false`，须用户确认才下载）不符，需查清并加固。

**排查过程**：
1. 读 `electron-updater@6.8.9` 源码：`doCheckForUpdates()` 中 `downloadPromise: this.autoDownload ? this.downloadUpdate() : null` → `autoDownload=false` 时不应下载；`checkForUpdates()` 入口无额外下载路径
2. 逐层排查调用方：`apps/web/src/useUpdate.ts` 只在 `check` 时调用、`UpdateBanner.tsx`/`UpdateCard.tsx` 的下载均绑定在按钮 `onClick`、`apps/web/src/api.ts` 仅转发 `window.dictAPI.update`、`apps/desktop/src/main.mjs` 的 IPC handler 无自动调用
3. dev 模式 + mock 更新源复现：日志 `check: autoDownload=false` → `check done: available=true hasDownloadPromise=false autoDownload=false` → **检查阶段不下载**
4. 打包版（`win-unpacked` + mock 源）复现：DIAG 状态停在 `phase:"available"`，无下载、无 IPC `update:download` 调用

**结论**：当前代码路径行为正确——检查到新版本后停在 `available`，等用户点「下载更新」。v0.4.0 那次的 `downloading` 未能在当前构建复现，判定为旧构建/当时环境差异，非当前代码缺陷。

**防御性加固（v0.4.2）**：
- `check()` 每次检查前重申 `autoUpdater.autoDownload = false`（防外部/库内部改写）
- 若 `checkForUpdates()` 仍返回 `downloadPromise`（库内部启动下载）→ 主动 `res.cancellationToken.cancel()` 并记日志 `unexpected auto-download detected → cancelling`
- IPC `update:download` 记录调用来源 URL（`e.sender.getURL()`），便于事后追溯
- 新增诊断日志 `check: autoDownload=…` / `check done: available=… hasDownloadPromise=…`

**验证**：打包版 + mock 源 → `phase=available` 且无下载 ✅；core 回归 71/0 ✅；发布 v0.4.2（含差分 blockmap，老用户可自动更新）

## 18. v0.6.0 词根表 / 词缀表（2026-09-16）

### 18.1 需求（用户原文）

三条指令指向同一件事：要一套**词根/词缀知识体系**——独立可浏览可搜索的词根表与词缀表、单词表按英/俄分离，并借此让单个词（如 тоска）能跳转到词根详情看到含义、词源与**全部同根词**。

### 18.2 勘察结论

- 词素零关联极少：俄语 20/432（4.6%）、英语 5/456（1.1%）→ 表格有实质内容可建
- **关联词不能用子串匹配**：`тоск` 子串在 59 个俄语词中出现，其中 `автосклейка`（авто+склейка）、`стетоскоп`（стето+-скоп）等与本词根无关
- **拆解算法本身是关联词污染源**：贪心「每步取最长」下 `стетоскоп` 在位置 3 命中 `тоск-`（忧愁），丢掉更优的 `стето- + -скоп`（观察镜）

### 18.3 拆解算法重写：贪心 → 全局最优分段（DP）

`packages/core/src/db/index.ts` 的 `breakdownWord`：

| 机制 | 说明 |
|---|---|
| **DP 最优分段** | `covered[i]` = 自 i 到词尾最大覆盖，`pieces[i]` = 对应最少片段；从根上消除位置抢占 |
| **首字符索引** | 每位置只比较同首字符词素（888 → 十位数），DP 反而比贪心更快 |
| **覆盖率阈值 0.55** | 整体覆盖不足判为「不可拆」，消除 `difficult→cul`、`run→un` 类碎片误拆 |
| **同分优先级** | 前缀 > 后缀 > 词根，否则 `unbelievable` 的 `un-` 被同名词根 `un` 顶掉 |
| **后缀位置约束** | 后缀左侧须有 ≥3 字符词干，消除 `ателье/тельце` 被 `-тель` 误拆 |

效果：`тоск-` 关联网从 21 条（含噪）→ **6 条全部正确**（тоска / тоскливый / тосковать / затосковать / стосковаться / истосковаться）。

## 21. v0.8.0 修复：词首单字符间隙的假词根误拆（2026-09-16，用户实测反馈）

> **版本**：v0.8.0（tag `v0.8.0` ⇒ `4c89272`；其后的 `55f8745` 为纯 `.board/` 清理）
> **触发**：用户查俄语 `плескание`（溅水），「词族」卡显示的是 **`лес-`（森林）** 的 40 个词——毫不相关的词族
> **一句话**：`breakdownWord()` 的两道「词首间隙」守卫**恰好都放过 `gap === 1`**，「词首单字符被跳过 + 词中撞上日常基础词根」的误拆全部漏网。本轮以**一行阈值改动**修复，并同步冻结「三把尺子」口径、建立独立判别集。

### 21.1 问题

| 查询的词 | 释义 | 被误配的词族 | 污染词数 |
| --- | --- | --- | --- |
| `плескание` | 溅水 | `лес-` 森林 | 40 |
| `хлестаться` | 抽打自己 | `лес-` 森林 | 40 |
| `анестезия` | 麻醉 | `нес-` 携带 | 40 |
| `ателье` | 画室/工作室 | `тел-` 身体 | 40 |

规模：全库 101,512 条俄语词条中 **342 词**呈此形态，其中 **267 词被误拆**、**75 词为真前缀**（后者保留，见 21.7）。

### 21.2 根因

`packages/core/src/db/index.ts` 的 `breakdownWord()` 用两道守卫拦截「词首有一段解释不了的间隙」的误拆：

```ts
// 守卫一（:846）：词头 1 字符间隙 + 单片段 → 判为不可拆
if (parts.length === 1 && parts[0].start === 1) return [];
// 守卫二（原 :859）：词首间隙 ≥2 且 gap 无法被前缀解释 → 判为误拆
if (parts.length && parts[0].start >= 2) { /* gapExplain */ }
```

- 守卫一要求 `parts.length === 1`，而 `плескание` 拆出 `лес-@1 + -ка@4 + -ние@6` 共 **3 段** → 不触发；
- 守卫二要求 `parts[0].start >= 2`，而它 `start === 1` → 不触发。

⇒ **`gap === 1` 正落在两道守卫的缝里。** 而假词根库偏偏只收日常基础词（`лес` 森林 / `тел` 身体 / `нес` 携带 / `лет` 飞 / `вер` 信），**最容易被撞上**。

**★ 覆盖率阈值对此完全无效**：`зверство` 覆盖 8/8 = **1.00**、`плескание` 8/9 = **0.89**，远高于 `BREAKDOWN_MIN_COVERAGE = 0.55`（`packages/core/src/db/index.ts:709`）。这是「阈值型防护」的固有盲区——只能靠**位置判据**修。

### 21.3 修复

一行改动（`packages/core/src/db/index.ts`）：守卫二阈值 `>= 2` → **`>= 1`**。

```diff
- if (parts.length && parts[0].start >= 2) {
+ if (parts.length && parts[0].start >= 1) {
```

语义上**不是新规则**，而是**补齐原规则的覆盖漏洞**：让 `gap = 1` 与 `gap ≥ 2` 适用同一条判据——「词首间隙必须能被库内某个前缀**精确解释**」，即 `:861` `const explained = all.some((x) => x.m.kind === 'prefix' && x.stem === gap);`。

**为什么不选「无条件禁止 `gap = 1`」**：对照组实测会额外误杀 `удачный`（真实拆解 `у- + да- + -ный`，词源 `удача`）。`в-` / `о-` / `с-` / `у-` **确实是俄语真前缀**（库内有 4 个单字符前缀词素），必须放行。

### 22.5 两项豁免与 `loses=2` 的正名

**① `loses = 2` 的正名（但数值保持为 2）**
`поднаковальня`、`поднакопить` 此前被拆成含**假词根 `дн-`（日、昼）**的双重错误拆解（形如 `по- + дн- + -ко + …`），现返回「不可拆」。`наковальня`（铁砧）的词源是 **ковать（锻造）**，与 `день`（日）无关 ⇒ **由假拆解转为不拆属净改善**。

**③ AC-11(c) 豁免：上升全部源自 `-ной` 一条 —— 并认定该判据存在结构缺陷**
留一法实测：口径A/B 的上升**全部来自 `-ной`**（去掉它 ΔA **+70** / ΔB **+71**，其余 7 条全为负）。
